# 8. The ICM-20948 (DMP3)

The ICM-20948's DMP is the same machine as chapters 1–7 describe, with a bigger address space
and real control flow. This chapter lists only what differs; everything not mentioned here
transfers unchanged and was checked on an ICM-20948 on the bench rig (`bench/probe42.py` to
`probe50.py`, ISA2.md Finding 24). Status tags mean the same as elsewhere, with **[HW]** now
meaning *measured on ICM-20948 silicon*.

## 8.1 Geometry

| | MPU-6050 (mantis) | ICM-20948 (DMP3) |
|---|---|---|
| DMP memory | 3072 B host-addressable, 1024 B program-addressable | **16 KB** (`0x0000`–`0x3fff`), all of it program-addressable **[HW]** |
| image load address | 0 | **0x0090** **[VENDOR]** |
| entry (`PRGM_START`) | 0x0300 / 0x0400 | **0x1000** (bank 2, register 0x50) **[VENDOR]** |
| data region | below the entry | `0x0000`–`0x0fff`, 4 KB; the 12-bit data pointer covers exactly this **[HW]** |
| code | entry to ~2270 B above | `0x1000`–`0x386c` in the stock image; free RAM to `0x3fff` |
| FIFO | 1024 B | **4096 B** **[HW]** |
| sample gate | `SMPLRT_DIV` | gyro ODR, `GYRO_SMPLRT_DIV` in bank 2: 1136 passes/s at divider 0 **[HW]** |
| registers | flat | four banks selected by `REG_BANK_SEL` (0x7f); DMP memory through `MEM_BANK_SEL`/`MEM_START_ADDR`/`MEM_R_W` = 0x7e/0x7c/0x7d in bank 0, 16-byte bursts that never cross a page **[VENDOR]** |

The stock image is 14301 B; because it loads at 0x90, its code begins at **image offset
0xf70**, not 4096. The bytes there (`d8 dc b8 b0 b4 f3 aa f8 f9 d1 d9 …`) are ordinary mantis
code.

Two bench traps that cost time: `USER_CTRL.FIFO_EN` must **stay set** while the FIFO is read
(with it cleared, `FIFO_R_W` returns one stuck byte and the count never moves), and the
register bank survives an ESP32 reset, so anything that identifies the part must select bank 0
before reading `WHO_AM_I` **[HW]**.

## 8.2 Pointers: the block field

`bc`, `bd`, `be` are not unknown here. Each adds one **1 KB block** to P0, P1, P2 respectively,
modulo 4, and the block resets to 0 at the start of every pass **[HW, probe47]**:

```
    addr = block*1024 + bank*256 + page*16 + 4*word         block, bank: 2 bits; page: 4 bits

    bc b3 8f  c0     reads 0x7f0            bc bc bc b3 8f  reads 0xff0
    bc bc b3 8f      reads 0xbf0            bc bc bc bc     wraps to 0x3f0
```

The order relative to the bank and page loads does not matter, and neither load resets the
block. This is why the vendor's runs of `bc`/`bd`/`be` are never longer than three, and why the
main body of the stock program opens with `be be bc bc bd bd` — all three pointers to block 2.

`bf` remains unattested.

## 8.3 Control flow: jump, call, return

`f4` is a **three-byte instruction** with a 16-bit big-endian absolute address **[HW, probe45/46]**:

```
    f4 hi lo      hi < 0x80     jump to  (hi<<8 | lo) & 0x3fff
                  hi & 0x40     ... as a CALL: e0 in the callee returns to the byte after lo
    f4 xx         xx >= 0x80    one byte, no jump; xx executes  (the MPU's bit-7 escape survives)
    e0                          RET   [HW]
```

- Backward jumps are legal — the stock image has 9 — so **loops exist on DMP3**. Nothing in the
  machine bounds them; a pass that loops forever stops the sample clock from being served.
- Calls nest at least two deep **[HW]**. The return address is not in RAM you can see.
- A plain jump into a routine that ends in `e0` kills the DMP after one pass **[HW]**: `e0` with
  no return address is not a halt.
- Predicates apply: `d9 f4 hi lo` and `da f4 hi lo` are the conditional forms (77 and 31
  occurrences); `da f1 ff` is the vendor's conditional halt, which also shows that a predicate
  **skips over mode bytes** to govern the next real instruction **[VENDOR]**.
- The MPU's 7-bit relative branch is gone. `f4 01 c2` on DMP3 jumps to 0x01c2 — into the data —
  and the DMP goes silent after one pass.

The stock image has 186 jumps, 56 calls into 15 routines at 0x349c–0x3859, and ends in `e0`.

## 8.4 Mode 4 and the I/O space

`f0`–`f7` are one 3-bit **mode register** and `f4` is its fourth value. Every `f4` — jump, call
or one-byte — leaves the machine in mode 4, and any `f0`, `f1`, `f2`, `f3` or `f5` (`f6`/`f7`
by symmetry, unmeasured) ends it; `d8`, `dc`, `dd`, `f8` do not, and it persists across passes
until `DMP_RST` **[HW, probe50]**.

While mode 4 is set, a **page load** (`8x`/`9x`/`ax`) resolves its pointer into an **I/O space**
instead of RAM: reads through it return a register map (index 0 reads `0xea` = `WHO_AM_I`,
0x74 reads `DATA_RDY_STATUS`, the word at 0x70 changes as the FIFO fills, 0x94–0xa9 hold
sensor-sized bytes) and stores through it reach no RAM address **[HW, probe47/48]**. A bank load
is unaffected. MOV with pointers loaded before the mode is a plain MOV; the ALU under the mode
did not store in the one test that could tell **[HW]**. The index mapping of the space is
**[INFER]**.

This is how DMP3 firmware touches the chip's registers, and it dictates the vendor's coding
discipline, which you must copy:

```
    <target>:   d8 f1 ...               every jump target re-arms a width mode first
    f4 75 a8  f4 75 c0  f1 ...          every call site is followed by f1 / f3
    f4  b9 af d0 c7  f3                 a one-byte f4 group: P2 -> I/O index, store word 3, leave the mode
    f4  c1  f1                          the smallest form: one MOV under the mode, then out
```

Forgetting the `f1` after a jump target is the DMP3 equivalent of a wild pointer: every page
load from then on addresses the I/O space, every read returns zero, and the fault shows up
one pass later.

## 8.5 What else differs

- `cc` under `f1` emitted the **full** 32-bit word **[HW, probe44]**. The MPU manual calls
  `c8`–`cf` a 16-bit MOV on the strength of vendor names alone; treat the width of that family as
  open on both parts.
- `d2`–`d7` (27 bytes in the image) and `e2`/`e7` (7) have no decode. `d2`–`d7` stand immediately
  before `fd`-discarded compares — `d5 fd 40 d6 fd 40 d7 fd 40` repeats one compare under three
  of them — so they read as TEST variants selecting a flag; `e2` sits in predicated slots right
  after a width byte (`da f0 e2`, `da f3 e2`), the shape of a conditional return. Both are
  **[INFER]** and listed in UNKNOWNS.md.
- No integer-submultiple rate drop. When a pass outruns the sample period the rate is simply
  1/pass-time **[HW, probe49]**.

## 8.6 Execution budget

`pass ≈ a × N + 16 µs`, fitted over the rate-dropped cells with residuals under 7 µs **[HW, probe49]**:

| instruction | ICM-20948 | MPU-6050 |
|---|---:|---:|
| `d8` predicate | 0.19 µs | 0.58 µs |
| `c0` MOV | 0.80 µs | 2.0 µs |
| `42` MUL | 1.18 µs | 7.9 µs |
| `40` ADD | 1.22 µs | 3.9 µs |
| fixed per pass | 16 µs | 56 µs |

A multiply costs the same as an add on DMP3. At the 880 µs period of divider 0, one pass holds
about 700 ALU operations or 1080 MOVs; at the stock 55 Hz setting (divider 19, 18 ms) the
budget is effectively unlimited for anything a human writes.

## 8.7 Toolchain

`tools/isa/decode.py` selects the `icm` lineage for any image over 14000 B, prints DMP addresses
(image offset + 0x90), resolves the SparkFun DMP3 data labels, follows the block field, renders
`JUMP`/`CALL`/`RET`/`MODE4`, and marks page loads made under mode 4 as I/O. The stock image
decodes to 99.67 % under this model. The assembler (`dmpasm`) does not yet know the ICM forms.

Bench side: `bench/icm.py` (register map, banked access, load, start, `Rig` helpers for custom
programs) and the probes named above. The bridge firmware auto-detects the part; the
`X`/`A`/`K` commands scan the bus, set the address and select the profile by hand.
