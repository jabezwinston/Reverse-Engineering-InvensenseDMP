# 8. The ICM-20948 (DMP3)

The ICM-20948's DMP is the same machine as chapters 1–7 describe, with a bigger address space
and real control flow. This chapter lists only what differs; everything not mentioned here
transfers unchanged and was checked on an ICM-20948 on the bench rig (`bench/probe42.py` to
`probe77.py`, ISA2.md Findings 24–27, 31). Status tags mean the same as elsewhere, with **[HW]** now
meaning *measured on ICM-20948 silicon*.

## 8.1 Geometry

| | MPU-6050 (mantis) | ICM-20948 (DMP3) |
|---|---|---|
| DMP memory | 3072 B host-addressable, 1024 B program-addressable | **16 KB** (`0x0000`–`0x3fff`), all of it program-addressable **[HW]** |
| image load address | 0 | **0x0090** **[VENDOR]** |
| entry (`PRGM_START`) | 0x0300 / 0x0400 | **0x1000** (bank 2, register 0x50) **[VENDOR]** |
| data region | below the entry | `0x0000`–`0x0fff`, 4 KB; the 12-bit data pointer covers exactly this **[HW]** |
| code | entry to ~2270 B above | `0x1000`–`0x386c` in the stock image; free RAM to `0x3fff` |
| FIFO | 1024 B | **4096 B** **[HW]** |
| sample gate | `SMPLRT_DIV` | gyro ODR, `GYRO_SMPLRT_DIV` in bank 2: 1136 passes/s at divider 0 **[HW]** |
| registers | flat | four banks selected by `REG_BANK_SEL` (0x7f); DMP memory through `MEM_BANK_SEL`/`MEM_START_ADDR`/`MEM_R_W` = 0x7e/0x7c/0x7d in bank 0, 16-byte bursts that never cross a page **[VENDOR]** |

The stock image is 14301 B (eMD 1.1.0; the eMD 1.0 build is 14290 B and differs by one 11-byte
edit, Finding 26); because it loads at 0x90, its code begins at **image offset
0xf70**, not 4096. The bytes there (`d8 dc b8 b0 b4 f3 aa f8 f9 d1 d9 …`) are ordinary mantis
code.

Two bench traps that cost time: `USER_CTRL.FIFO_EN` must **stay set** while the FIFO is read
(with it cleared, `FIFO_R_W` returns one stuck byte and the count never moves), and the
register bank survives an ESP32 reset, so anything that identifies the part must select bank 0
before reading `WHO_AM_I` **[HW]**.

## 8.2 Pointers: the block field

`bc`, `bd`, `be` are not unknown here. Each adds one **1 KB block** to P0, P1, P2 respectively,
modulo 4, and the block resets to 0 at the start of every pass **[HW, probe47]**:

```
    addr = block*1024 + bank*256 + page*16 + 4*word         block, bank: 2 bits; page: 4 bits

    bc b3 8f  c0     reads 0x7f0            bc bc bc b3 8f  reads 0xff0
    bc bc b3 8f      reads 0xbf0            bc bc bc bc     wraps to 0x3f0
```

The order relative to the bank and page loads does not matter, and neither load resets the
block. This is why the vendor's runs of `bc`/`bd`/`be` are never longer than three, and why the
main body of the stock program opens with `be be bc bc bd bd` — all three pointers to block 2.

`bf` remains unattested.

## 8.3 Control flow: jump, call, return

A branch target is a **16-bit big-endian absolute address** in the two bytes after an `f4`
**[HW, probe45/46]** — and, because `f4` puts the machine in branch-target mode (§8.4), in any
two bytes that begin with a value below 0x80 until that mode ends **[STATIC + HW, Finding 26]**:

```
    f4 hi lo      hi < 0x80     jump to  (hi<<8 | lo) & 0x3fff
                  hi & 0x40     ... as a CALL: e0 in the callee returns to the byte after lo
    f4 xx         xx >= 0x80    one byte: no jump, xx executes, the mode is entered
    hi lo         hi < 0x80, while the mode is set:  the same jump / call, no f4 needed
    e0                          RET   [HW]
```

- Backward jumps are legal — the stock image has 12 — so **loops exist on DMP3**. Nothing in the
  machine bounds them; a pass that loops forever stops the sample clock from being served.
- Calls nest at least two deep **[HW]**. The return address is not in RAM you can see.
- A plain jump into a routine that ends in `e0` kills the DMP after one pass **[HW]**: `e0` with
  no return address is not a halt.
- Predicates apply: `d9 f4 hi lo` and `da f4 hi lo` are the conditional forms (77 and 31
  occurrences); `da f1 ff` is the vendor's conditional halt, which also shows that a predicate
  **skips over mode bytes** to govern the next real instruction **[VENDOR]**.
- The second form is how the vendor writes if/else and a call on a fall-through path:
  `f4 16 14  d8 17 74` (if-jump, else-jump), `d9 f4 14 33  d8 74 ad` (if-jump, else call
  0x34ad). The eMD 1.0 / 1.1.0 image pair moved every one of these low bytes by the size of
  the one code edit between the builds, exactly as it moved the 232 `f4` targets.
- A conditional jump that is **skipped** by its predicate still enters mode 4 **[HW, probe64 C]**:
  the fall-through needs its `d8 fX` as much as the target does, or the next page load is an
  I/O load (which is how a count-up loop can run forever with its counter untouched).
- The MPU's 7-bit relative branch is gone. `f4 01 c2` on DMP3 jumps to 0x01c2 — into the data —
  and the DMP goes silent after one pass.

The stock image has 186 jumps, 56 calls into 16 routines at 0x349c–0x386c, and ends in `e0`.
Everything in it is reachable from the entry point: there is one program and no interrupt
vector (the DMP raises interrupts, §8.7, it does not take them).

## 8.4 Mode 4: branch-target mode, and the I/O space

`f0`–`f7` are one 3-bit **mode register** and `f4` is its fourth value. Every `f4` — jump taken,
not taken or skipped by a predicate, call, or the one-byte form — leaves the machine in mode 4; any `f0`–`f3`, `f5`, `f6` or
`f7` ends it **[HW, probe50, probe54]**. It is **one global flag**: a callee's `f1` clears it for
its caller, a callee that ends in `f4 e0` leaves its caller in it, and it persists across passes
until `DMP_RST` **[HW, probe54b]**.

While mode 4 is set:

- **every byte below 0x80 is the high half of a branch target**, not an ALU op **[HW]**. The
  bytes at or above 0x80 are ordinary instructions: `d8`–`db`, `dc`/`dd`, `bc`–`be`, MOVs,
  `f8`–`fb` and the rest all execute (beacon-tested: none of `f8 f9 fa fb fc fe` is ever read as
  a target half);
- a **page load** (`8x`/`9x`/`ax`) resolves its pointer into an **I/O space** instead of RAM:
  reads through it return one byte per word from an internal register file (index 0 reads
  `0xea`; live sensor-sized bytes at 0x1d0 and 0x250–0x2a4 in one snapshot) and stores through
  it reach no RAM address **[HW, probe47/48/56]**. It is **not the host's register file**: the
  host's INT_ENABLE, XA_OFFS and DATA_RDY_STATUS are not visible through it and a store at their
  indices changes no register **[HW, probe56]**. Its index map is **[INFER]**. A bank load is
  unaffected; a MOV whose pointers were loaded before the mode is a plain MOV. `bf`, unused by
  the vendor, sends P2 the same way: a store after it lands nowhere **[HW, probe54 E]**.

There is no ALU under mode 4 — the earlier "the ALU did not store" was the ALU byte being read
as a target. This is what dictates the vendor's coding discipline, which you must copy:

```
    <target>:   d8 f1 ...               every jump target re-arms a width mode first
    f4 75 a8  f4 75 c0  f1 ...          every call site is followed by f1 / f3  (the callee's own
                                        f1 has already cleared the flag; the vendor is belt and braces)
    f4  b9 af d0 c7  f3                 a one-byte f4 group: P2 -> I/O index, store word 3, leave the mode
    f4  c1  f1                          the smallest form: one MOV under the mode, then out
```

Forgetting the `f1` after a jump target is the DMP3 equivalent of a wild pointer: the next low
byte becomes a jump into wherever its two bytes point, and every page load until then addresses
the I/O space.

`fc` is not a prefix on DMP3 but a **three-byte bit test**, `fc X Y` (§8.5), and its two operand
bytes are consumed under the mode like any instruction's — the vendor's
`d9 f4 hi lo  d8 fc c0 08 d9 f4 hi lo` is *if-jump; else if P1 word 0 bit 1 is set, jump*
**[HW, probe57/76]**.

## 8.5 Predicates and the flag

DMP3 has **one flag, F**, and its predicates are **sticky** **[HW, probe52, probe54 D]**:

```
    any ALU op, INC, DEC     F := (result < 0)  -- only while NO predicate is armed (under d8)
    fc cX Y  BIT             F := bit of P1 word (X&3) chosen by Y (04/08/10/20/40/80 = bits 0-5). Nothing stored
    d1                       F := (result == 0)           the TEST, replaces the sign
    d9  IF.F      da  IF.not-F      db  IF.F (identical to d9 in every cell)
    d8  ALWAYS    ends a predicate; so does the next d9 / da / db
    MOV, CLR and SHIFT leave F alone
```

**While `d9`/`da`/`db` is armed, ALU ops, INC and DEC do not touch F; `d1` and `fc` do**
**[HW, probe60]**. A predicated block therefore cannot disturb its own condition, and every
test that decides the next block has to run under `d8` — the vendor's `d8 fc c0 00 d9 f4`.

`fc X Y` is a **three-byte bit test** of a config word, not the MPU's swap prefix
**[HW, probe57/76/77]**: it stores nothing, leaves no ALU result, and sets F from one bit of
P1 word (X & 3). Y selects the bit: `04`/`08`/`10`/`20`/`40`/`80` test word bits 0–5 (F set
when the bit is set), `00` tests the low 6 bits all clear, `01` the complement. This is the
feature dispatcher: `fc c1 04` at 0x14cf tests bit 0 of `DATA_OUT_CTL2`, and the vendor walks a
bitmask with `fc c0 04 … 08 … 0c … 10`. The full decode of a non-one-hot Y (the op-field bits
crossed with the selector) and reach above bit 5 are partly mapped (UNKNOWNS.md §7).

A not-taken predicate skips *everything* — MOVs, pointer loads, ALU ops, the halt — until
the next `d8`–`db`. Mode bytes (`f0`–`f7`) between a predicate and its instruction are
transparent (`da f1 ff` is a conditional halt). This gives the two vendor idioms:

```
    31 d1 d9 f4 10 36        compare (RSUB, discarded or not), TEST, if equal jump
    d8 fc c0 08 d9 f4 ..     if P1 word 0 bit 1 is set, jump  (the feature gate)
    d8 .. f9 da f4 <loop>    decrement the counter under d8; while it has not gone negative, jump
    d9 a9 f8 d8 f2 af        conditionally: point P2, increment; then ALWAYS resumes
```

Put a `d8` after every conditional block. Forgetting it is the DMP3 equivalent of an
unterminated `if`: the rest of the pass silently disappears whenever the condition is false.

A loop's counter must be decremented with no predicate armed: `loop: f1 dd c0 dc f9 da f4
loop` runs away for every count above 0, because the DEC runs under the `da` that the taken
jump left armed and F stays frozen; `loop: f1 dd c0 d8 dc f9 da f4 loop` terminates for every
count **[HW, probe58/60]**. `programs/loop_icm.s` is the working form; the vendor's other
shape (compare at the top with `fc`, INC at the bottom, unconditional jump back, 0x1af1–0x1bfb)
obeys the rule because its `d8` follows the conditional exit. (That shape's exit test is a `fc` zero
test of a flag word, not a count compare; a count compare is an RSUB stored somewhere harmless
followed by `d9`/`da`.)

The MPU has the same design, re-measured on 2026-09-12 (Finding 28): sticky predicates, a flag
set by every op and frozen under an armed predicate. Its one difference is at zero — the MPU
keeps N and Z, `d9` is IF (N ∨ Z) and `da` is IF ¬N, and `d1` clears N — so an MPU `d9` fires
on a zero result where DMP3's does not.

## 8.6 Multi-precision: the shifter and the product's low word

The register the shifter works on is loaded by **every ALU op** as well as by `d4`–`d7` — the
last loader wins — and after a MUL it holds the **64-bit product** **[HW, probe64]**. So
`20 fd 3f` is "add, then halve", `2a fd 0f` after a multiply stores the product scaled by 2^15
with the low word's bits pulled up, and shifts compound. A MOV does not touch the register; a
shift with nothing loaded since reset stores 0.

`fd` is not NOSTORE on either part (on the MPU it exchanges P0 and P2, Finding 28). On DMP3 `fd n`
is a **two-byte shift** of a 4-word register that
`d4`–`d7` load from P0 **[HW, probe51, 28/28]**:

```
    d4 | d5 | d6 | d7       load 4 words from P0's page; select word 0 | 1 | 2 | 3 for the store
    fd n                    shift, then store the selected word through the route
                              n[4:0] = s
                              n[5] = 0   left by s; each word takes the top of the NEXT word's
                                         30-bit fraction at its bottom (word 3 wraps to word 0)
                              n[5] = 1   arithmetic right by 32 - s, per word
                              n[6]       pre-advance P2 first
```

The register keeps its shifted contents, so consecutive `fd` compound; a bare `fd` with
nothing loaded since `DMP_RST` stores 0. The words are 30-bit Q30 fractions: the
four-word register is one long Q30 number, and

```
    df df df f1  d4 fd 70  d5 fd 70  d6 fd 70  d7 fd 70          (stock image, 0x383c)
```

shifts all four words right by 16 into P2's four words.

The multiplier is double precision: the ALU op stores the Q30 result (`product >> 30`) and
**`d2`** stores the **low 30 bits, sign-extended from bit 29**, over the current P2 word
(`d3`: advance first) **[HW, probe51]**. After an ADD the low word is 0.

```
    2a d2  f0 00 d2  a9 de                                   (stock image, 0x367c)
```

## 8.7 Interrupt, and the two clears

- **`e2` raises DMP_INT1** **[HW, probe53]**. Under a predicate it fires only when the
  condition holds; the vendor's `da f0 e2 f1` is "if not zero, interrupt". This is how a DMP3
  program tells the host a packet is ready (on the MPU the drivers used `f4 4x`).
- `e7` clears M[P2] in place, indistinguishable from `de` **[HW]**. One vendor site.
- INC/DEC (`f8`–`fb`) read and write M[P2] and set F from the result **[HW, probe52]**.
- FSYNC reaches the chip (`EXT_SYNC_SET` puts it in `TEMP_OUT_L` bit 0) but no instruction
  measured reads it **[HW]**.

## 8.8 What else differs

- **`c8`–`cf` copy the word with its half-words exchanged** **[HW, probe54 C]**: `c8` under `f1`
  writes `45670123` from `01234567`; under `f2` the source's *low* half lands in the destination's
  upper half (`4567ee00` over `c0ffee00`), under `f3` the source's *high* half lands in the lower
  (`c0ff0123`). The decoder renders them `MOVX`. The MPU does the same (Finding 28); MOV16 was the
  vendor's name.
- No integer-submultiple rate drop. When a pass outruns the sample period the rate is simply
  1/pass-time **[HW, probe49]**.
- Every byte value the stock image uses now decodes: **100 %** of its 10 349 code bytes.

## 8.9 Execution budget

`pass ≈ a × N + 16 µs`, fitted over the rate-dropped cells with residuals under 7 µs **[HW, probe49]**:

| instruction | ICM-20948 | MPU-6050 |
|---|---:|---:|
| `d8` predicate | 0.19 µs | 0.58 µs |
| `c0` MOV | 0.80 µs | 2.0 µs |
| `42` MUL | 1.18 µs | 7.9 µs |
| `40` ADD | 1.22 µs | 3.9 µs |
| fixed per pass | 16 µs | 56 µs |

A multiply costs the same as an add on DMP3. At the 880 µs period of divider 0, one pass holds
about 700 ALU operations or 1080 MOVs; at the stock 55 Hz setting (divider 19, 18 ms) the
budget is effectively unlimited for anything a human writes.

## 8.10 Toolchain

`tools/isa/decode.py` selects the `icm` lineage for any image over 14000 B, prints DMP addresses
(image offset + 0x90), resolves the SparkFun DMP3 data labels, follows the block field, renders
`JUMP`/`CALL`/`RET`/`MODE4`/`SHIFT`/`STORE.LO`/`INT`/`MOVX`/`TESTZ`, keeps a predicate armed until the
next `d8`–`db`, reads a two-byte target for every byte below 0x80 while mode 4 is set, and
marks page loads made under mode 4 as I/O. Both stock images decode to 100 % under this model.

The assembler knows the DMP3 forms under `.lineage icm` (`programs/loop_icm.s` is the counted
loop of `probe55`): `.org`, labels, `jump`/`call LABEL`, `ret`, `mode4`, `if f`/`if nf`,
`p0blk`/`p1blk`/`p2blk`, `load k`, `shl s[,adv]`/`sar s[,adv]`, `lo`/`lo.next`, `int`, `clr`, `bit k,n`/`bitz k`.
It refuses an ALU op, `emit` or a low `.db` byte while mode 4 is armed (they would assemble
to branch targets) and warns about a jump target that does not begin with a width byte;
`branch` is rejected in this lineage.

Bench side: `bench/icm.py` (register map, banked access, load, start, `Rig` helpers for custom
programs) and probes 42–77. The bridge firmware auto-detects the part; `X`/`A`/`K` scan the
bus, set the address and select the profile by hand, and `Y 0|1` drives FSYNC (D4).
